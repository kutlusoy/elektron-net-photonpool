# Changelog

## 0.2.0-rc1 (release candidate for the first mainnet test)

Pool (`photond`)
- Pagination for every list that grows: miner page (pending credits, payouts, blocks found, workers), pool page (blocks, payouts, devices) and operator page (miners, blocks), 20 rows per page with a bar `1-20 of 137  ‹ newer  older ›`. New data: `creditsTotal` and `/public/v1/account/<address>/credits`, `blocksTotal` and `payoutsTotal` in `/public/v1/pool`, `offset` for `/public/v1/blocks` and `/payouts`.
- Miner page: all blocks found and all payouts of an address, page by page (`‹ newer` / `older ›`, 20 per page); the account view carries the first page and the totals (`blocksTotal`, `blocksByMode`, `blocksByStatus`, `payoutsTotal`, `payoutsSum`), further pages come from `/public/v1/account/<address>/blocks` and `/payouts` (`offset`, `limit` up to 100). The pending list shows up to 150 credits. Test: `test/step36_account_pages.py`.
- Registry: the log now also says when an explorer accepted a report (`registry: block <hash> reported to <explorer>: attributed`).
- Engine view: block announcements that arrive together (the same block found in two modes, several blocks at once) stack under each other instead of overlapping.
- Payouts no longer fail on a chain without fee estimates (`Fee estimation failed. Fallbackfee is disabled`): the pool takes the fee rate from the explorer (`explorer_url`, `/api/v1/fees/recommended`, one-hour target, at least 1 sat/vB), falls back to 2 sat/vB (`payout.fee_rate_fallback`) and still honours a fixed `payout.fee_rate` (`PAYOUT_FEE_RATE` in the stack). After a failed payout run the pool waits at most 8 times the interval before it tries again (was 64 times).
- Payout schedule on the pages: `/public/v1/pool` reports `payout` (dry run or live, interval, next and last run). The pool page (Modes pane) and the miner page (Balance pane) show it, with a warning while payouts are in dry run.
- Block attribution through the Elektron Net registry: the pool reads `mempools.txt`, reports every block it found to the listed explorers and answers their call back at `/api/pool/identity/confirm` (true only for its own recent blocks). `[registry]` in `photond.toml`, `REGISTRY_REPORTING` in `stack.conf`; the name is the pool name, so `POOL_NAME` and `DOMAIN` must match the line in `pools.txt`. Guideline: `doc-elektron/guideline-pool-registry-reporting.md`, test: `test/step34_registry_reporting.py`.
- Search and AI visibility: readable tab titles (`Photon Pool for Elektron Net | Fast SHA-256d Mining Pool`, `Engine | ...`), description, Open Graph, Twitter card and JSON-LD metadata, `/robots.txt` and `/llms.txt` (what Elektron Net and Photon Pool are, the public API, how to mine).
- Release name `v<node>-p<pool>` (for example `v4.0.6-p0.2.0-rc1`, a full release `v4.0.6-p0.2.0`): the node part is `NODE` in `src/version.rs`, the pool part is `version` in `Cargo.toml`. Both APIs report it as `release`; the web footer shows it together with links to Elektron Net, Elektron Mobile, Elektron Mempool, the website and X.
- PPLNS end-to-end test (`test/step33_pplns_scenarios.py`): encrypted wallet and passphrase, wrong passphrase, shares, fee split, maturity, payouts, restart, 120 accounts in batches, orphaned block, minimum payout. Fixes found by it: shares were rejected when the node signalled a version bit inside the miner rolling mask; `payableAccounts` ignored the minimum payout.
- Stratum V1 server with vardiff, version rolling, empty `extranonce1` and `extranonce2_size = 0`, lock-free work allocation; 15,000 simulated connections on one 4-core box in 115 MB RSS.
- Payout modes solo (direct coinbase payout, no fee), PPLNS and PPS in one pool; mode per port or `m=` in the password; PPS paused until the wallet reserve is funded.
- SQLite ledger, maturity tracking (101 confirmations), batched `sendmany` payouts with crash recovery, dry-run by default, encrypted wallet support.
- Depth view in all three web pages: a pane can be maximized (button, double-click on its title, click on a pane in the background, Esc to go back); the other panes recede in 3D and blur.
- Interactive neon charts in the maximized panes (hashrate, latency, share quality, worker distribution, blocks, payouts) with draw-in animation and hover read-out, and sortable table columns (click a header): `ui/charts.js`.
- Optional background music in all three pages (`ui/music.js`): an original generative dark-synth score synthesized with the Web Audio API (no audio files), about 10 min 10 s before it loops, with play, pause, stop and volume controls in the title bar. It only starts after a click.
- Background music from audio files: put mp3/ogg/... files into `music/` (mounted into the container, `music_dir` for bare metal) and the player in the title bar plays them as a looping playlist (previous, next, play, pause, stop, volume) with a credit tooltip from `music/playlist.json`. Audio files and the playlist stay out of git (license). Without files the built-in generated score is used.
- Bitaxe (ESP-Miner) support found by the first hardware test: fresh jobs marked clean for the agents in `[stratum] clean_work_agents`, job cadence from `version_space_bits` (default 5), a duplicate share triggers a new job, and jobs are kept for 10 s so that late shares are found (first result: 98.8 % duplicates, then 83 % "job not found").
- Self-adjusting pool: the job interval of every connection is learned from its duplicate and stale shares (`[stratum] adaptive_jobs`, `adaptive_min_interval_ms`), and the number of candidates in use follows the work demand (`[pool] autoscale_candidates`, `min_candidates`; the Docker stack now provisions 512 pool addresses). Measured with simulated Bitaxes up to 15,000 connections without overlapping units.
- Music resumes at the first click or key press of the next visit (same track and position) when it was playing; pause and stop switch that off. History by device type (one line per Bitaxe, NerdMiner, ... in the history pane, `/public/v1/history/devices`, `[ledger] device_history_minutes`, default 5), kept for `stats_keep_days` like the pool history.
- Public pages as a single-page app (router, views, view transitions): the music keeps playing when changing between the pool and the miner view. Device list by user agent (Bitaxe, NerdMiner, cpuminer, ... with links and the open source star, best share per device type) in the public and operator UI and APIs (`/public/v1/devices`, `/api/v1/devices`), and stored pool history (`/public/v1/history`, `[ledger] stats_keep_days`, default 60, older samples are deleted) with a range switch. Only the data API is rate limited.
- One app on both ports: the operator page is merged into the single-page app. POOL, ENGINE and MINER are served on the public port from aggregated data and a sanitized event feed (`/public/v1/engine`, `/public/v1/events`); the OPS view (workers, blocks, ledger, console) is loaded only where the admin API answers. The old `app.js` and `public.html` are replaced by `ops.js`, `engine.js` and `index.html`.
- Slow miners (CPU, small devices) no longer get dropped: vardiff also runs on the job timer and lowers the difficulty 32-fold when a window brings no share, and every connected miner counts as online (before, a miner that found no share for 2 minutes showed as offline and was closed by the idle timeout).
- ENGINE view with a live 3D scene next to the event feed (Three.js r149, MIT, vendored in `ui/vendor/` and loaded only for that view; light 2D scene when WebGL is missing): node with rays and sparkles at the horizon, a stream of photon fire, attestation ring, block template assembled from the candidates, allocator units, share check gate, miners and Photon gateways, all driven by real counters. The public engine data now carries aggregate Photon numbers (gateways, channels, shares, checks) and share counts; device groups are capped (24 unknown names, rest "Other").
- Node RPC hardened after an external review (the patch mechanism of the Docker setups, `PHOTON_NODE_PATCHES` and `NODE_PATCHES`, is gone because the node branch contains the code): overflow-safe summing, a budget over the whole request (400,000 outputs, 8 MiB of scripts), the per-candidate work runs outside `cs_main`, at most two parallel calls, coinbases above half a block are refused. New tests `step28` (limits, responsiveness), `step30` (blocks mined through the real pool in pool and solo mode are accepted by an unpatched node) and `step29` (an unpatched node accepts the blocks, wrong attestations are rejected). See section 6b of `guideline-batch-attestation-rpc.md`.
- The Docker setups build the node from the branch `photonpool` of `elektron-net`, which contains the `getattestationbatch` RPC (always available, no node option); `ELEKTRON_REF` goes back to `main` once it is merged there. A node without the RPC makes the pool fall back to one `getblocktemplate` call per address.
- Load test `test/load_mainnet_utxo.py` of the batch RPC with a UTXO set of up to 10 million outputs and 2000 mempool transactions: latency about 0.1 s for up to 512 candidates and 0.35 to 0.45 s for 4096, independent of the size of the set, `cs_main` held about 100 ms per call; results in section 6c of `guideline-batch-attestation-rpc.md`.
- Job pace: the shortest job interval keeps its default of 200 ms and grows with the number of connections so that `max_jobs_per_sec` (default 50,000) is never exceeded. A trial with 25 ms made a Bitaxe slower (0.28 to 0.4 TH/s against 0.6 to 0.8), because every fresh job is a clean job for it; the defaults were restored. The pool learns per device type (hash rate, job interval, clean jobs, kept in the ledger, `/api/v1/learned`) and starts new connections of that type with it, else with a typical rate of the chip named in the user agent.
- Public pool page and personal miner page on a separate listener with rate limiting; terminal-style operator UI and read-only admin API.
- Candidate backends: `gbt` (one `getblocktemplate` per payout address, unmodified node) and `batch` (`getattestationbatch`, node branch `photonpool`), `pool.backend = auto`.
- Photon protocol (`src/photon/`): framing, messages, Noise transport, payout plan, accounting tree, coinbase check, share verifier, pool session (`[photon]` in `photond.toml`, off by default) and `photond gateway` with a Stratum V1 front end for ASICs (`gateway.example.toml`) and a CPU miner for tests. The first Bitaxe test uses the normal pool Stratum port.

Node RPC (branch `photonpool` of `elektron-net`)
- `getattestationbatch`: one call attests many coinbase candidates (about 0.07 ms per candidate). Only code is added, no consensus code path is changed. Always available in that node, no option. The reference diff of the source changes is `test/photonpool-node.patch`.

Docker
- `docker-compose.yml` (node and pool) and `stack/` (node, pool, Caddy with HTTPS, encrypted wallet). The node is built from the branch `photonpool` of `elektron-net` (back to `main` once the code is merged there).

Tests (`test/`)
- 20 integration steps, a spot check load test with simulated gateways (`test/load_spotchecks.py`, `photond photon-load`) against unmodified regtest nodes with an independent Python attestation oracle, 61 Rust unit tests, a differential test of the batch RPC and a full-block load simulation (11,000 transactions per block, 10,000 miners).

Photon spot checks
- Per-tip budget (`max_checks_per_tip`, default 8) and concurrency limit (`max_concurrent_checks`, default 2); a node that cannot answer makes a check inconclusive instead of failing the gateway; the gateway splits large attestation requests below the node's 32 MB RPC limit. Load figures in `doc-elektron/guideline-photon-protocol.md` section 14c.

- Gateway trust is remembered per address and per payout script (kept in the ledger), spot checks are selected proportionally to each gateway's own probability, a payout script is banned for an hour after three failed checks.

- One gateway serves several payout addresses: Stratum users `<payout address>.<worker>` get their own Photon channel (`max_channels_per_connection`, default 64), each owner verifies its own credit.

- Gateway reconnects to the pool with backoff, keeps ASICs working on the plans it holds, re-opens its channels and re-announces the template; fatal errors (wrong key, ban, protocol mismatch, failed proof) are not retried. The pool saves share aggregates and trust on `SIGINT`.

Review and operation
- First review pass over all Photon code (`doc-elektron/guideline-photon-review.md`). Fixed: announced difficulty was trusted (a gateway could have earned credit without work), unbounded memory per connection, a panic aborting the whole pool (release profile now unwinds), no per-address connection limit, quadratic trust-book pruning, unlimited proof requests, IPv6 trust evasion. Robustness tests for the decoders.
- `systemd/`: units for pool, gateway and node, sysusers file, installer (`DESTDIR` supported).

- Protocol guideline: prior art section (DATUM, Stratum V2 Job Declaration, P2Pool) and an analysis of where the accounting commitment lives, header growth (factor 1.45 if it were in the header) and the effect of pruning; the payout outputs, not the commitment, are the real UTXO growth risk.

- Photon payout plans (rules version 2): everybody with a credit is paid, no minimum amount, parts per billion instead of per million, at most `max_outputs` (default 200) per block with the smaller credits taking turns above that. The node RPC reserves block weight for the largest coinbase of a request (a full block with a 128-output coinbase would otherwise exceed the weight limit). Capacity limits are documented in the protocol guideline (6.3); the gateway warns when a job exceeds the 16 KB line limit of ESP32 miners.

- Gateway: every unit of work gets all 16 version bits (5.5 times less Stratum traffic to the ASICs with a 200-output coinbase: 94 instead of 518 Mbit/s for 1,000 ASICs of 200 TH/s, measured with simulated ASICs), and the number of coinbase variants follows the hash rate of the attached ASICs automatically (`max_variants`).

- Protocol guideline: section 7.2 explains UTXO set growth (created minus spent outputs), when it shrinks (merging payouts), what the plan does to it and what operators can monitor.

- Test at the node: the cost of validating and attesting a block stays the same while the UTXO set grows 31-fold, and follows the number of transactions (`step23`).

- `systemd/Caddyfile.example`: Caddy with automatic HTTPS in front of the public pool page for installations without Docker, documented with the matching `[public]` settings.

- All configuration files list every option with its default and the accepted values in comments (`photond.example.toml`, `gateway.example.toml`, `docker/photond.docker.toml`, `docker/elektron.conf`, `stack/stack.conf.example`, the systemd environment templates). Tests check that the examples load, that every option of the code is documented in them and that the defaults they show are the real ones. Fixed in the pool example: the spot check budget had been written under `[payout.pplns]` instead of `[photon]`.

Known limits
- No real ASIC hardware test yet (first one: Bitaxe, see `doc-elektron/guideline-release-and-bitaxe-test.md`), Stratum V2 not implemented, no mainnet-scale benchmark, Docker images not yet built in CI.
